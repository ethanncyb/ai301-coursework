# Rubric: is this reproduction package ready to post?

Six required checks and one preferred. Each one judges the outcome the package
shows, never the shape of the write-up: a terse report with an exact artifact is
ready, and a long, well-formatted one whose artifact shows something else is not.

In eval mode the bundle is the whole world: the issue context, the repo-facts
block, the candidate claim comment, and the candidate repro report. In live mode
the drafts are the candidate side and the issue-side evidence comes from the
locations named in `references/evidence-guide.md`.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record, read against the version and platform the issue targets (the issue body, its thread highlights, and what maintainers say they confirmed it on). Live mode: the draft's environment line against the issue thread. Evidence guide: Environment. | Both of: (a) **recorded** — the report names the product version it ran and every platform dimension the issue's behavior turns on (the OS or build where the issue is platform-specific, plus any component the issue names as load-bearing, such as the driver, shell, backend, or install method); (b) **deviation stated** — where the version, platform, or build differs from what the issue targets or what it was confirmed on, the report says so in its own words. Fail if there is no environment record, if a dimension the issue turns on is absent, or if the run used a version the issue does not target and the report does not name the difference. A deviating environment is not itself a failure: naming it passes, hiding it fails. | required |
| steps-rerunnable | The steps, commands, inputs, and configuration in the repro report, read as a stranger holding only this comment and the recorded environment. Evidence guide: Steps. | All of: (a) **reachable starting state** — the inputs, files, or config are shown inline, are public and named precisely enough to fetch, or are described precisely enough to rebuild with the element that triggers the behavior named; (b) **executable steps** — each step is an action with its target (a command, a UI action, a config value), not a summary of one such as "set up the project" or "configure it as usual"; (c) **reaches the trigger** — the sequence arrives at the condition the issue names. Fail if any load-bearing step runs inside private code, an unshared config, or a setup described but never shown. Terseness is not a failure: four exact commands re-run where ten paragraphs of prose may not. | required |
| artifact-shows-issue | The output excerpts, logs, or screenshots in the repro report, read line by line against the behavior the issue describes: its error text, exit status, or symptom. Evidence guide: Behavior shown. | Either: (a) **reproduced** — an artifact is present and the behavior it shows is the issue's behavior, matching on the deciding particulars (the same message, the same failure mode, the same input path or syntax the issue names), not merely an adjacent failure of the same tool; or (b) **evidenced cannot-reproduce** — the report states it could not reproduce, shows the attempt it actually ran with its artifacts, and accounts for the gap: either the attempt reached the issue's trigger conditions, or the report names the specific condition it could not satisfy and why that condition looks necessary. A cannot-reproduce need not reach the trigger; it must show the attempt and locate what was missing. Fail if there is no artifact at all, if the report claims a reproduction whose artifact shows only that the tool ran or the app started, or if the shown behavior differs from the issue's on a deciding particular: a graceful validation error where the issue reports a crash, a compile error where it reports a runtime error, the process still alive where it reports it dying. | required |
| outcome-honest | Every assertion in the claim comment and the repro report — what was reproduced, what is confirmed, what the cause is, how widely it applies — set against what the artifacts actually show and what was actually run. Evidence guide: Honesty. | All of: (a) a stated reproduction is carried by an artifact that shows it; (b) a stated cause or mechanism is carried by a trace, a diff, or a cited finding from the thread, not asserted from plausibility; (c) the stated scope does not exceed what was run — no widening to untested versions, platforms, or builds, and parts of the issue left untested are named as untested. An honest cannot-reproduce that says so plainly and names what differed passes in full; it is a faithful outcome, not a weak one. Fail confident language resting on an artifact that does not support it, causes asserted without evidence ("obviously", "I verified this race condition", "guaranteed reproducible"), and conclusions widened past the environment tested. | required |
| claim-specific-and-modest | The candidate claim comment, read against the issue body and thread. Evidence guide: Comms. | Both of: (a) **specific** — the comment names something true of this issue in particular: the symptom, the version or environment it was seen on, a file, function, or pointer from the thread, or the concrete next step it will take. A comment that would read identically pasted on any other issue fails, as does a bare "+1", a me-too, or an assign-me with no stated intent; (b) **modest** — it promises investigation and a report back, nothing more. Fail a promised fix, a stated deadline or turnaround, a guarantee, or a request to reserve or lock the issue. Naming a direction ("I would like to work toward the acceptance test suggested above") is not a promise; "I will fix it within 2 days" is. | required |
| conventions-respected | The repo-facts `contribution policy` line, read against both candidate comments. Live mode: `CONTRIBUTING.md` in the repo root or `.github/`, any `AI_POLICY.md` or `AI_USAGE_POLICY.md` it links, and the issue templates. Evidence guide: Comms. | Every requirement the repo actually states about comments is met. The two that recur: (a) **disclosure** — where the policy requires AI usage to be disclosed, at least one comment names the assistance and its extent; work produced in this course is AI-assisted, so saying nothing is a miss rather than an exemption; (b) **human voice** — where the policy requires comments to maintainers in the contributor's own words, the comments read as written by their author rather than as generated boilerplate. Two things pass: a policy silent on AI, and a policy that welcomes or conditions AI use without asking for disclosure — responsibility, understanding, human review, testing, and "fully AI-generated contributions are not accepted" are terms to honor, not disclosure asks. A disclosure requirement the policy scopes to pull requests does not bind an issue comment. Fail only a requirement the repo states and the comments do not meet. | required |
| control-run-shown | The repro report, for a second run that varies one condition: the trigger removed, an alternate input, or a known-good version. Evidence guide: Behavior shown. | The report includes a contrast run that isolates the trigger, so the artifacts show the behavior follows from the condition the issue names rather than from the setup around it. Ranks only: a single complete reproduction is ready to post without one. | preferred |

## Verdict rule

Accept if and only if all six required checks pass. Any single required fail
rejects the package: a reproduction is a proof, and a proof with one broken
step is not ready to go upstream. `unclear` counts as fail — evidence a reader
cannot verify is evidence that is not ready to post.

`control-run-shown` is preferred and never changes a verdict. Report its grade,
and among packages that are ready, prefer the ones that carry a control run.

On a claim-only live draft the repro report does not exist yet, so
`env-recorded`, `steps-rerunnable`, `artifact-shows-issue`, and
`control-run-shown` report `unclear` with evidence `not yet applicable:
claim-only draft` and leave the verdict rule. `claim-specific-and-modest` and
`conventions-respected` apply in full, and `outcome-honest` applies to the
assertions the claim comment itself makes. The verdict then answers only
whether the claim comment is ready to post.
